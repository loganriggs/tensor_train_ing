# H100 day-1 acceptance run

Run from the checked-out repository, in the installed Python environment, on a node with at least two visible GPUs. Set the actual **whole-node** hourly price, the GPU's dense BF16 peak TFLOPs/s (not its sparse peak), and immutable train/held-out validation manifests:

```bash
scripts/h100_day1.sh \
  --output /workspace/h100-day1-001 \
  --manifest /workspace/data/train/manifest.json \
  --validation-manifest /workspace/data/heldout/manifest.json \
  --gpu-hourly-rate-usd "$NODE_HOURLY_RATE" \
  --peak-tflops-per-gpu "$DENSE_BF16_TFLOPS"
```

The output directory must not already exist. The command writes an aggregate `report.json` with stage results and log paths, stops at the first failure, and keeps evidence for diagnosis. It does not modify existing experiment runs. Run `scripts/h100_day1.sh --help` for stage skip flags and budget/time controls. A report with skipped stages is partial evidence, not full node acceptance.

The sequence is environment inventory, CPU regression suite, GPU kernel tests, NCCL equivalence, a two-rank and all-rank tiny trainer replay check, polynomial attention tuning, then a 200-update all-GPU pilot. The smoke compares uninterrupted training with an interrupted/resumed trajectory, including checkpoint state. The tuning output is recorded; it does not automatically change kernel defaults or claim those tiles were used in the subsequent canary.

The generated pilot configuration records changes from `configs/pilot_1b.yaml`: real data paths and price, a bounded token horizon, isolated ledger, and reduced checkpoint retention. Two runtime limitations are explicit: distributed training runs without `torch.compile`, and active QK clipping is disabled because the distributed trainer does not support it. Batch-bound recording remains enabled and every update must supply a finite `score_bound_max`. This is an infrastructure/performance canary, not validation of the complete long-run recipe.

The canary reports global and per-GPU prediction tokens/s using the sum of slowest-rank update durations, both for all updates and excluding the first ten startup updates. End-to-end throughput also includes initialization and checkpoint I/O. These measure different costs; the startup exclusion does not claim LR warmup has finished. Memory includes each rank's peak allocated and reserved CUDA bytes. MFU uses `6 * total_parameters * global_tokens_per_second / (GPU_count * supplied_peak_FLOPs_per_second)`; it is approximate and excludes attention-specific FLOPs. Record the correct hardware peak in the command so results remain interpretable.

Completion requires the full requested update count, finite nonnegative losses and score bounds, and matching token totals. These checks do not establish convergence or a safe long-run learning rate. The held-out validation manifest is pinned in configuration; the day-1 canary does not run a quality evaluation. The training ledger budgets trainer work; environment/tests/tuning also consume rental time outside that ledger.

The runbook's report, fail-fast behavior and metric arithmetic are CPU-tested. Actual NCCL, H100 kernels, all-rank memory and pilot throughput must be measured on the rented node; a mocked test pass is not a hardware result.
