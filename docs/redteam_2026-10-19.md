# Red-team of runs, architecture and data (2026-10-19 22:45, Claude)

Asked by the user: "is there anything that's subtly wrong or could screw us up down the road?" Each item is marked **verified** (checked with a
command whose output is quoted) or **unverified** (a risk I reasoned about but did not test).

## A. Verified and fixed

### A1. Discarded micro-batch rows → ~2× data consumption and silent repetition (the important one)
- **Mechanism (verified in `tnlm/train.py:436-470`, `tnlm/distributed_train.py:366-375`):** each update's target quota is filled with whole
  micro-batches; the excess targets of the last one are masked away (`_mask_to_count`) but its rows were already read from the stream.
  A 16×512 micro-batch holds **8165–8197 targets** (rows carry 509–512; 2,000 sampled, median 8180). So the default **8192**-target quota
  needs a 2nd micro-batch almost every update: **input read = 1.96× tokens trained** (`input_tokens_seen / tokens` = 1.9595 in
  muon_followup, 1.0625 at 131k batch = 17/16 micro-batches). `PackedSampler.next_batch` **silently starts epoch 2** when a split runs out
  (`tnlm/data.py:786`).
- **Past runs affected (scan of 208 finished stages):** `lr_horizon` 10 stages read up to **1.89 epochs** of the 320M set, so its 300M-token
  points trained on ~half-repeated data. That rule (LR_opt ∝ D^−0.10) sets the H100 LR, the Chinchilla-100M LRs and the grid LRs. One
  high-LR `joint_transfer` stage (1.93×). Nothing else wrapped; all 50M-token screens fit inside one epoch (98M ≤ 320M).
- **Would have hit:** the grid's s67m (5.2B input vs a 3.0B set), s191m (14.8B vs 12.6B), s304m (23.8B vs 12.6B: half the run repeated),
  chinchilla100m (3.9B vs 3.0B); the H100 run at 1.25× (35B input for 28B trained).
- **lr_horizon impact, resolved 09:16 Oct 20:** the redo on fresh data is flat across 3.2e-4–9e-4 at 300M (all within 0.011), so the repeated data
  did not move a measurable optimum; the H100 LR is unchanged.
- **Fixes:** quota **8160** for every not-yet-started grid size and chinchilla100m (never needed a 2nd micro-batch in 2,000 samples; 1.0025×);
  s38m (running; fits: 2.99B of 3.01B) and its LR checks keep 8192 for comparability. H100 configs **261120 = 4 rounds × 8 ranks × 8160**
  (at context 2048 a 4-row micro-batch holds ≥ 8167), guarded in `tests/test_h100_configs.py`. `scripts/scaling_grid.py` now fails any stage
  that read past one epoch. **`configs/lr_horizon2`** re-runs the 300M horizon points on the 13B set (queued). **Codex (HIGH, COORDINATION
  22:45):** carry unused rows over instead of discarding them; fail rather than wrap epochs silently; record the input/trained ratio.

### A2. The H100 context (2048) has never been trained
- **Verified:** all 100 evaluated runs trained at context 512; `configs/h100/*.yaml` use 2048. This attention has no softmax normalization, so its
  sums run over up to 4× more positions, and none of the LR, batch, stability or Muon findings were measured there.
- **Result (01:38 Oct 20):** stable for all three; rankings preserved; ~15% slower; no loss benefit yet at 50M tokens (ties at its own
  context). Keep 2048 for H100. Details in docs/scaling.md "Context 2048".

### A3. H100 data sizing was off by 2×
- **Verified:** tokens are int32 (`tnlm/token_format.py`: `TOKEN_DTYPE = '<i4'`), so 28B tokens ≈ 112 GB + ~26 GB documents, not "56 GB at 2 B/token"
  (`docs/h100_readiness.md` §3, now corrected). Rental disk must be sized for that.

### A4. Long-horizon Muon vs AdamW comes too late
- Muon's advantage was measured at 50M–200M tokens (−0.14 at 8k batch, −0.044 at 131k batch), and Muon gains are reported to shrink with training
  length. The only 2B-token Muon vs AdamW test (chinchilla100m) was last in the queue, behind ~9 days of Muon-only grid. **Moved ahead of s101m.**

## B. Verified OK

## C. Unverified risks (not tested tonight)
1. ~~Near-duplicate validation contamination~~ **checked 23:10 (`scripts/check_contamination.py`): minor.** 13-gram overlap of the 4,496 val-split
   documents (evaluation scores the first 1,476) with a 600M-token (4.8%) sample of the 13B training split: 1.6% of windows found, median per-doc
   overlap 0%. 15 docs ≥ 50%, none ≥ 90%. The top ones are site templates (Beatport login text, shop review boilerplate, an AARP event notice,
   a university course page) that recur across many pages, not leaked articles. Effect: a few short val docs are easy for every model (slightly
   lower absolute CE; may flatter larger models' template memorization). Negligible for A/B comparisons. Note when interpreting the fit's E.
2. **Single seeds.** Most conclusions rest on 1 seed (2 for spectral and Muon at 512). Seed-to-seed spread is ~0.01–0.02 at 100M, so effects ≤ 0.02
   (spectral −0.025 at 100M, the A/B tie at 1B) are within noise.
3. **Muon's non-hidden LR is fixed** (`aux_adamw_lr` 4.5e-4 for embeddings/unembedding/gains at every width and batch). That could favour some
   sizes in the grid and isn't tuned for H100.
4. **Total-parameter scaling laws at small sizes are embedding-dominated** (s38m: 67% embedding). Kaplan vs Chinchilla's disagreement is largely
   this. `fit_scaling_law.py --params nonemb` gives the other view; report both.
5. **Variant B (spectral_rms) can't use QK-clip.** If the H100 run diverges at long context or high LR, there's no in-run rescue. A2's test covers
   the context part. It also shows heavy-tailed MLP products at high LR (kurtosis 23–48k), a risk for low-precision inference.
6. **Grid LR is one constant per size across 5–40 tokens/param**, set with an AdamW-measured horizon rule (Muon's own horizon behaviour is
   untested until chinchilla100m).

## D. Round 2 (2026-10-20 03:20; "did we find all the bugs? where haven't we looked?")

### D1. The multi-GPU trainer can't run the H100 recipe as written (verified)
`tnlm/distributed_train.py` raises on `compile` ("compile is unsupported"), on QK-clip ("QK clipping currently supports serial training only") and on
periodic stability logging. Its docstring says "CPU/gloo is the tested path": it has never run on GPUs/NCCL here (single-GPU box). Consequences:
- **Variant A (pre_rms + QK-clip) cannot launch on 8 GPUs**, and its main safety mechanism doesn't exist there. B (spectral) and Muon don't need it
  (B robust at 3× LR without clip; Muon keeps attention scores small). This is a new argument for B and/or Muon.
- **The H100 throughput and cost estimates assumed compiled speed.** Measured 15:55 Oct 20: compiled is only **1.06×** eager at 1B (micro-batch 1×2048), so the penalty is ~6%.
- **No divergence telemetry** in the distributed run (the stability watcher depends on serial-only logging).
- Fixed: `compile: false` in both H100 configs (guard test). A's QK-clip is marked BLOCKER in its config. Codex asked (COORDINATION 03:20, HIGH) for
  distributed QK-clip, the compile-penalty measurement, and distributed stability logging.

### D2. Checked and fine (verified)
- **Distributed Muon orthogonalizes full matrices**, not shards: `tests/test_distributed_muon.py` compares sharded updates with serial ones
  (≤ 4e-4) and asserts that the naive per-shard version differs (> 4e-4).
- **The sampler shuffles documents** (per-epoch permutation, `PackedSampler._order`), so training doesn't walk dumps in file order.
- **Padded vocab rows are never scored** (`model.py:239`, unembedding sliced to `vocab_size` before the CE).
- **Evaluation matches training**: s38m tpp40 eval CE 4.1865 vs last-200-step training loss 4.1815 ± 0.016.

2. **Checkpoint/resume over days at H100 scale** (recovery cadence, disk, mid-run resume equivalence on GPU): tested serially on CPU only.
3. **bf16 numerics of the polynomial attention at 1.4B × 28B tokens**: products of activations can overflow bf16 range later in training than any

4. **Tokenizer/data edge cases** (very long documents, non-English, code). Never inspected beyond the contamination check.
5. **The analysis/interpretability tooling** (tensor-network extraction, `tnlm analyze`) was reviewed only for normalization cost, not for

6. **Optimizer state/precision choices** (Muon momentum dtype, AdamW eps, weight decay on gains) were inherited, never ablated.
