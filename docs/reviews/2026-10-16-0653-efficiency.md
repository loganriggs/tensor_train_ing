## Largest finding: trainer steps are 2.7× slower than the bare loop
**[Update 08:55: resolved.** On an idle GPU, Codex's matched measurement of current `train_run` is 68.2k tok/s (96.5% of a
matched bare loop on real batches, `runs/codex_gpu_efficiency_20261016/`). The confirmation sweep was running a code
snapshot frozen at 06:54, which predated Codex's compiled row-bucketing fix (Dynamo recompile-limit fallback).
Re-snapshotting current code gives 67.4k tok/s in the sweep itself. The two runs finished on old code are kept in
`runs/confirmation/v2_oldcode/` as a cross-version check. My 99.5k "bare" figure used synthetic fixed document layouts
and isn't a matched baseline.]
The 50M-token confirmation run (100M model, 8192 tok/update, compiled, Triton attention, chunked CE) steadily
takes **0.229 s/step = 35.7k tok/s**. The same model and batch in a bare fwd+bwd+AdamW loop
(`scratch/profile_breakdown.py`) takes 0.083 s/step (99.5k tok/s).
- Ruled out: optimizer-exposure bookkeeping (0.4 ms), batch hashing (0.1 ms), metric writes (8 KB/step), GPU sharing
  (one process), clocks (2.6 GHz, 191/250 W), a forced reference backend (`auto` resolves to Triton), periodic stalls
  (median = p90; only step 1 is slow).
- Contributes: `PackedSampler.next_batch` takes **20 ms in Python**, serially with the GPU. There are also several host syncs
  per step (validation `.any()`/`int()`, `float(loss)`, `int(actual_n)`, `clip_grad_norm_(error_if_nonfinite)`, an explicit
  synchronize), which stop the CPU from queueing ahead.
- Unexplained: GPU utilization reads 79%, so most of the gap is GPU-side work, not host stalls alone. That needs a
  contention-free `torch.profiler` trace of `train_run` (py-spy can't attach: no ptrace in this container).
- Cost: the confirmation sweep will take about 9 h instead of about 3.5 h (about $4 instead of $1.50). Results are still valid. At funded
  scale, a 2.7× slowdown would be the single largest cost item, ahead of any kernel work.
