# Bounded-space sequential sweep staging

Implemented and integrated into the canonical package after isolated development and review. Claude confirmed the running experiments use a frozen snapshot; no files under runs/confirmation were changed.

The opt-in API is `run_sweep(..., prune_completed_intermediates=True)` and CLI flag `sweep --prune-completed-intermediates`. Ordinary sweep retention stays unchanged. This policy retains every parent/cooldown initialization and final checkpoint, all checkpoint manifests, metrics, evaluation reports, comparison outputs and cost records. After a candidate's evaluation succeeds, it may remove only intermediate `milestone-*/state.pt` and `recovery-*/state.pt` files owned by that sweep. That includes the consumed cooldown branch payload; its manifest and parent identity remain, but it is no longer a resumable checkpoint. Future recovery/forking must use retained checkpoints.

Each deletion is bound to an artifact hash and a durable planned cleanup record. Cleanup verifies surviving and retained files before deletion and recovers from interruption after any deletion without rerunning completed charged stages. The shared billing lock prevents cooperating admissions from pinning a payload during deletion; external nonterminal/reserved parent references reject cleanup. Ancestor checks and directory-FD no-follow traversal reject symlink redirection. This is not a guarantee against a privileged hostile writer. The final snapshot inventory must account for exactly the journaled removals; extra or changed files remain errors.

Storage admission must cover cumulative retained outputs plus the active candidate's peak working set, rather than summing every candidate's full intermediate peak. It remains an advisory estimate, not a reservation or guarantee against other writers. Per-training-launch and per-checkpoint admission remain active. Retained initial/final checkpoints still grow with candidate count; this is reduced intermediate storage, not constant total storage for an arbitrarily large sweep.

Existing sweeps cannot switch this policy silently: it is part of frozen execution identity. This feature must not delete artifacts from Claude's current runs during development or validation. Tests use isolated temporary CPU runs.

Independent planning arithmetic for the current six-candidate `candidates_s101.yaml` grid gives 205.820 GB with all intermediates retained, versus 102.911 GB maximum cumulative-retained-plus-active storage, ending with 74.844 GB estimated initial/final retention. Decimal GB, conservative checkpoint projections; manifests/metrics remain and arbitrary metadata or concurrent writes can exceed planning allowances. Evidence: `runs/codex_staging_storage_audit/forecast.json`. The implementation will be checked against this independent calculation.

Usage: add `--prune-completed-intermediates` to a new `tnlm sweep` invocation. With `project.dry_run: true`, the same command reports the sequential retention forecast without launching; plan with the same flag intended for execution. Ordinary `plan_search` continues to report its existing checkpoint projections. Nine new retention tests and 16 existing sweep tests pass; independent review checked pruning paths, ledger locking, partial deletion replay and forecast math. Full integrated CPU regression: 651 tests passed, three warnings, 177.79 seconds; CUDA kernel/parallel files excluded.
