# Tokenizer identity for checkpoint probes

A validation manifest can be pinned and checksummed while assigning different meanings to the same integer token IDs. Previously, ordinary checkpoint evaluation and analysis did not compare its tokenizer to the training tokenizer. Vocabulary bounds and exact-document overlap checks cannot detect that mismatch.

Both entrypoints now validate tokenizer compatibility before constructing the sampler or model. Production manifests must declare GPT2 with EOS 50256, valid SHA256 fingerprints, and matching vocabulary hash, regex and special-token metadata. Package/version metadata can differ when the declared encoding semantics agree. The tokenizer fingerprint generated by prepare_data covers the sorted vocabulary ranks, regex and special tokens.

Injected offline tokenizers have no equivalent fingerprint. They are permitted only for CPU probes when both manifests explicitly declare injected/test_only and all tokenizer metadata matches. Reports label this `test_only_metadata_match`, not production encoding evidence. Mixed production/fixture data and missing or malformed production identity fail closed.

Successful evaluation reports and analysis invocation provenance retain the identity check, both manifest hashes and the matched metadata. This binds the declared encoding to checksummed manifests; it does not independently re-tokenize the entire source corpus. The existing checkpoint loader still verifies the training manifest against the checkpoint, and artifact integrity checks remain in the sampler.

The current FineWeb pilot and confirmation manifests independently pass the production check, with fingerprint `5e915a49323da8b419011d3c3c0f1d098da4302b46c9b54ca83761860eafca94`. No token data or final-test examples were sampled for this check. Calibration already uses the same training manifest in both trainers; it has no separate dataset override.

Validation: 98 existing evaluation/analysis/training/sweep integration tests pass (28.83 seconds, one warning), plus 18 new independent compatibility tests, including actual GPT2 preparation and both entrypoints rejecting before sampler/model construction. No CUDA execution; fake availability is used only to verify early fixture rejection.
